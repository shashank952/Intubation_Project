Airway MD

A clinical decision-support tool that predicts how hard it will be to place a breathing tube (intubation) into a patient before the operation. It reads 30 clinical measurements, runs them through a trained machine-learning model, and returns a risk class — Easy, Moderate, or Difficult — plus an AI-written explanation for the anesthesiologist.

Multimodal · 3-Class PyTorch TabTransformer FastAPI + MongoDB Next.js 14 + Tailwind LLM Assistant Docker + CI/CD

01 · The Big Picture

What problem does this solve?

? The clinical problem

When a patient is put to sleep for surgery, a doctor (anesthesiologist) must slide a plastic tube into the windpipe so the patient can breathe. Sometimes this is easy, sometimes it is very difficult — and a difficult airway that is not predicted can be life-threatening.

Today this judgement relies on the doctor's experience and a handful of bedside tests. This project turns those tests into data and uses a machine-learning model to give a second opinion: a risk class and a risk percentage, backed by an AI explanation.

The output is always 1 of 3 classes:

🟢 Easy — standard intubation 🟠 Moderate — use alternatives & a backup plan 🔴 Difficult — advanced techniques + senior staff

✓ What was actually built

  • A synthetic dataset of 2,500 patients (balanced across the 3 classes).
  • A TabTransformer deep-learning model trained on 30 features → 85.9% accuracy / 0.970 AUC.
  • Two extra baseline models (XGBoost, Random Forest) for comparison.
  • A FastAPI backend with login, patient records and predictions.
  • A Next.js dashboard where a doctor fills a form and sees the result.
  • An LLM assistant that writes a clinical summary and recommendations.
  • Docker + GitHub Actions so everything can be shipped and re-run.

i The whole project in one sentence

A doctor logs into a web dashboard, types 30 measurements about a patient, and the system returns a risk score (0–100), a class (Easy/Moderate/Difficult), a confidence level, and an AI-written clinical report — all stored safely in a database for later review.

Why this matters: in real hospitals, most airways are easy, so a model can get high accuracy while never spotting a hard case. A balanced dataset forces the model to learn all three classes properly.

05 · Data Preprocessing

Turning raw inputs into numbers the model can read

A neural network only understands numbers. Raw text like "Female" or "Yes" must be converted, and raw numbers like BMI (which range from ~15 to ~50) must be scaled so no single feature dominates.

Key rule The same scaler that was fitted during training is saved to disk (checkpoints/tabular_scaler.pkl) and re-loaded by the API at prediction time. This guarantees the live inputs are scaled exactly like the training inputs — a common bug in ML projects that this one handles correctly.
Ordinal vs one-hot Mallampati is ordinal (Class I → IV has a natural order), so it is encoded as an ordered integer (0–3). Yes/No and disease flags become simple 0/1 binary values. The TabTransformer then learns its own rich embeddings from these integers.

The TabTransformer is a neural network designed specifically for tabular data (data that sits in a spreadsheet, like this one). Instead of treating every column as a plain number, it learns a rich "embedding" for each categorical value and lets the features talk to each other using self-attention.

Nine steps at a glance

  1. Read 7 numerical + 22 categorical inputs.
  2. Preprocess numericals with StandardScaler, categoricals with LabelEncoder.
  3. Tokenize: project 7 numericals to 1 token; embed 22 categoricals separately.
  4. Concatenate to 23 tokens and add learned positional encoding.
  5. Transform with 3 × (attention → add/norm → FFN → add/norm).
  6. Mean-pool the 23 tokens into one 64-d vector.
  7. Project 64 → 128 with output_proj.
  8. Classify 128 → 128 → 3 logits.
  9. Serve: softmax at T=5, then weighted risk score.

1 Read the patient row

The form supplies 7 numerical measurements and 22 categorical answers. In training, StandardScaler centers and scales the numericals, and LabelEncoder turns each category into an integer 0…card−1.

numerical [B, 7] · 22 categorical vectors [B] each

2 Turn values into tokens

numerical_proj = nn.Linear(7, 64) maps all seven numbers to one 64-d token. In parallel, 22 independent nn.Embedding(cardinality, 64) tables map each category to its own 64-d token. The .clamp(0, num_embeddings−1) guard keeps an out-of-range index from crashing inference.

[B, 7] → [B, 1, 64] · 22 × ([B] → [B, 1, 64])

3 Concatenate into a sequence

torch.cat([x_num] + x_cat, dim=1) stacks the numerical token and the 22 categorical tokens into a [B, 23, 64] matrix. Token 0 is the numerical profile; tokens 1–22 are the categorical columns. This is the sequence the transformer actually reads.

4 Add positional encoding

A learned parameter pos_encoding of shape (1, 23, 64) is added to the matrix. Attention is permutation-invariant on its own, so this is what tells the block which position each token occupies. The shape does not change.

x = x + pos_encoding[:, :23]

5 Run the transformer block — three times

The block keeps the shape [B, 23, 64] and performs four operations:

  • 5a · Self-attention. Q/K/V, 4 heads × 16 dims, softmax(Q·KT/√16)·V.
  • 5b · Add + LayerNorm 1. x = LayerNorm(x + Attention(x)).
  • 5c · Feed-forward. 64→256→64 with GELU and dropout 0.3.
  • 5d · Add + LayerNorm 2. x = LayerNorm(x + FFN(x)).

Stacked 3×; each block has its own weights.

6 Mean-pool the tokens

x.mean(dim=1) averages across the 23-token axis, turning [B, 23, 64] into [B, 64]. The result is one fixed-size summary vector per patient, independent of token order.

7 Project to 128 dimensions

output_proj = nn.Linear(64, 128) expands the pooled summary into the patient embedding used by the classifier: [B, 64] → [B, 128].

8 Classify

The head is Linear(128→128) → GELU → Dropout(0.3) → Linear(128→3). It outputs three raw logits, one for each class: Easy, Moderate, Difficult.

9 Softmax, class and risk

The API divides the logits by a temperature of 5.0 and applies softmax, yielding three probabilities. argmax gives the predicted class and its confidence. The router then blends the probabilities into the risk score:

risk = (0·P(Easy) + 50·P(Moderate) + 100·P(Difficult)) ÷ 100

🧩 Why a transformer for a spreadsheet?

Traditional models treat each column independently. A transformer lets the model compute relationships like "when Mallampati is IV and neck movement is low, the combined risk is higher than either alone". Self-attention is exactly the mechanism that captures these interactions — it is the same idea behind modern language models, but applied to clinical columns instead of words.

The project plan also designed a full multimodal version (tabular + 5 image types fused with cross-attention). That code exists (image_encoder.py, fusion.py) but is not used in production because no real image data is available yet — so the shipped model is tabular-only.

07 · Risk Score

How the risk percentage is calculated

The model does not output a single number — it outputs a probability for each of the three classes (they add up to 100%). Those three numbers are then turned into one clean risk score between 0 and 1 (shown to the doctor as 0–100%).

Step 1 · The model gives three probabilities

After the classifier head, a softmax function converts the raw scores into probabilities. Example output for one patient:

Easy 10%
Moderate 25%
Difficult 65%

The class with the highest probability becomes the prediction (here: Difficult), and that probability becomes the confidence (65%).

Step 2 · The weighted risk formula

Each class is given a fixed weight — Easy = 0, Moderate = 50, Difficult = 100 — and the probabilities are used to blend them into one number:

weighted = (0 × P(Easy)) + (50 × P(Moderate)) + (100 × P(Difficult))

risk_score = weighted ÷ 100   // result sits in the range 0.0 – 1.0

Worked example (the patient above):

weighted = (0 × 0.10) + (50 × 0.25) + (100 × 0.65)
        = 0 + 12.5 + 65 = 77.5

risk_score = 77.5 ÷ 100 = 0.775 → shown in the UI as 78 / 100 (78% risk)
0–33Low · Easy
34–66Moderate
67–100High · Difficult
Temperature softening (a safety tweak) Before the softmax, the backend divides the raw scores by a temperature of 5.0. This "flattens" the probabilities so the model is not over-confident — important because the data is synthetic and an over-confident wrong answer is dangerous in a clinical tool.
Where the score is stored The final risk_score (plus the class, confidence and all three probabilities) is saved in the predictions collection in MongoDB, so every past assessment keeps its exact result.
08 · The AI Assistant

How the LLM writes the clinical report

The ML model gives numbers. The LLM (Large Language Model) turns those numbers plus the patient's profile into a short, human-readable clinical summary and a set of recommendations for the anesthesiologist.

🧾 What goes into the prompt

The backend assembles a strict, structured prompt (see backend/deploy/llm_assistant.py):

# SYSTEM PROMPT (rules for the model)
Anesthesiologist decision-support for a
difficult-airway prediction (Easy/Moderate/
Difficult). Use ONLY provided patient data,
never invent values. If confidence < 60%,
note uncertainty. Frame as risk and
preparation, never guaranteed outcomes.

# USER PROMPT (assembled per patient)
Patient Profile:
  Age: 54, Gender: Female, BMI: 32.9 ...
  Mallampati Score: 4, TMD: 6.1 cm ...

Model probabilities: Easy: 10%, Moderate: 25%, Difficult: 65%

Return ONLY 5 concise bullet points.
- Each line must start with "- ".
- Keep every bullet under 18 words.

🛡 Safety design choices

  • "Use only provided data" — the LLM may not invent lab values.
  • Bullet-only output — consistent, scannable clinical text.
  • Uncertainty rule — below 60% confidence it must say so.
  • Non-blocking — if the LLM is down, the API still returns a valid (fallback) report and the dashboard shows an "AI unavailable" banner.
  • Feasibility check — responses shorter than 15 characters are rejected and retried.

Login returns a JWT token, which the browser stores and sends with every request. The backend reads the user's role fresh from the database on each request, so a downgraded or deleted user loses access immediately.

13 · Why It Looks Like This

The design language: Neo-Brutalism

The app (and this document) uses Neo-Brutalism — thick black outlines, hard offset shadows, flat loud colours and big bold type. It is intentionally the opposite of the soft, grey, gradient-heavy "generic SaaS" look.

🎨 The rules

  • 3px black borders on every card, button and input.
  • Hard offset shadows (4px 4px 0 #111) — never blurred.
  • Flat colours — no gradients on core UI (cream, yellow, cyan, lime, pink, orange).
  • Buttons "press" — on hover they shift into their own shadow.
  • Bold typography — Playfair Display for headings, Inter for body, JetBrains Mono for technical values.
  • High contrast — black text on light panels, yellow-on-black accents.

💡 Why it fits a clinical tool

  • Clarity under pressure. A doctor reading a risk result needs instant hierarchy, not decoration. Brutalism is unambiguous.
  • Colour = meaning. Green/orange/red map directly to low/moderate/high risk everywhere in the app, so the eye learns the language instantly.
  • Distinctive & memorable. It does not look like every other medical dashboard — deliberate, confident, easy to demo.
  • Accessible by default. Thick borders and high contrast help low-vision users and work on cheap hospital monitors.

🎛 Risk colour system (used across the whole app)

🟢Easy · green-500
🟠Moderate · warning-500
🔴Difficult · danger-500

The background is a warm cream (#F5F1DC) in light mode and near-black (#121212) in dark mode, so long shifts don't strain the eyes.

🧭 Read the diagram in 3 layers

  1. Presentation — the doctor + browser + Vercel-hosted Next.js UI.
  2. Application — the Render-hosted FastAPI backend, which owns all logic (auth, ML inference, risk scoring, LLM calls, DB access).
  3. Data & AI services — MongoDB for storage, the external LLM for text, and the trained model loaded in the backend's memory.

🔒 Trust boundaries

  • The browser never touches MongoDB or the model directly — only the API.
  • Every protected call carries a JWT; the API re-checks the role from the DB.
  • Patient data leaves the system only to the configured LLM endpoint, and only as the structured prompt the backend builds.
  • Images are built once in CI, stored in GHCR, and deployed as immutable containers.
