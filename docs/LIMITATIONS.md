# 🔴 1. Labels are made up, not observed

### What's wrong
The model is trained on `data/dataset.xlsx`, but the `Target` column in that file was **not recorded
from real patients**. It was calculated by a function in the code:

`scripts/generate_synthetic_data.py:200` → `_assign_target()`

That function adds points for Mallampati score, TMD class, neck circumference, BMI class, age, and a
few other fields, then splits the result into three equal groups.

### Why it matters
The model learns to reproduce a rule that was written by hand from the same inputs. That is not
prediction — it is a lookup table. It can never discover anything the rule didn't already know, and
it can never warn you that the rule is wrong.

### Evidence
Re-applying the project's own rule to the project's own data reproduces the stored labels only
**about 78 %** of the time (the rest is the injected random noise — see #3). The exact figure moves
by roughly ±1 point per run, because the rule re-draws its own noise every time it is called.

### How to fix it
1. Add four evidence columns to the patient spreadsheet, filled by a human from the theatre record:
   `CL_grade`, `Attempts`, `Adjunct`, `Rescue_device`.
2. Derive `Decision` from those four columns with a fixed, written rule.
3. **Never** derive `Decision` from the measurements in the same row.

See the rule in section 2.

# 🔴 2. Classes are forced to 33 / 33 / 33

### What's wrong
`generate_synthetic_data.py:250-255` splits the risk score at the 33rd and 66th percentile, so the
dataset contains exactly one third of each class.

Measured distribution of `Target` in `data/dataset.xlsx`:

```
Easy 33.3 %   Moderate 33.4 %   Difficult 33.3 %
```

### Why it matters
Real difficult intubation happens in roughly **5–15 %** of patients, not 33 %. Forcing equal thirds:

- teaches the model a prior that is wrong by 3–6×
- makes **PPV meaningless** — the number a clinician actually acts on
- destroys probability calibration (which is why the temperature hack in #8 exists)

A screening tool that says "Difficult" one third of the time is not a screening tool.

### How to fix it
1. Label from real outcomes.
2. **Keep the real prevalence.** If Difficult is 8 %, the training set should be 8 % Difficult.
3. Report prevalence-dependent metrics: PPV, NPV, sensitivity at a fixed operating point.
4. If you must rebalance, do it with `class_weight`, never by changing the label distribution.

# 🔴 3. The accuracy ceiling is a random-number generator

### What's wrong
`generate_synthetic_data.py:246` adds Gaussian noise to the score before assigning classes:

```python
scores += np.random.normal(0, 1.0, len(df))
```

### Why it matters
That line makes roughly **22 % of the labels unlearnable** — the label no longer matches the
features for those rows. So every model trained on this file is capped at about 0.80–0.86 accuracy,
no matter how good it is.

`0.859` therefore does not mean "the model is good". It means "the model reached the ceiling that
one line of code imposed".

### How to fix it
1. Delete the noise term from the generator so nobody regenerates a "valid" dataset by accident.
2. Stop reporting accuracy from this file as a result.
3. If you need a synthetic smoke-test set, keep it clearly labelled as synthetic and never cite its
   metrics.

# 🟠 4. The deep model adds nothing over a shallow baseline

### What's wrong
The production checkpoint is a TabTransformer with **180,483 parameters**, trained on 2,500
synthetic rows (72 parameters per row).

### Evidence
Same table, plain gradient-boosted trees, no tuning:

| Model | Parameters | 5-fold CV accuracy | Recall Easy / Moderate / Difficult |
|---|---|---|---|
| HistGradientBoosting | thousands | **0.804 ± 0.010** | 0.88 / 0.71 / 0.82 |
| TabTransformer (checkpoint) | 180,483 | 0.859 | — |

### Why it matters
The transformer buys nothing measurable and costs 180 k parameters. On the 125 real patients it
would be ~1,445 parameters per patient — certain overfitting. It also makes the project harder to
explain in a viva for zero benefit.

### How to fix it
1. Make XGBoost / LASSO the baseline and report it first.
2. Only keep the transformer if it beats the baseline with **non-overlapping confidence intervals**.
3. Report parameter count against sample count so the trade-off is visible.

# 🔴 5. The 125 real patients have no outcome column

### What's wrong
`data/raw/merged_laryngoscopy.xlsx` is 125 rows × 30 columns: 29 measurements + `Patient_ID`.

There is **no** Easy / Moderate / Difficult column. The source spreadsheets
(`AI laryngoscopy.xlsx`, `AI laryngoscopy2.xlsx`) contain only predictors — no Cormack–Lehane
grade, no attempt count, no outcome of any kind.

### Why it matters
You cannot train on "original data only" because there is nothing to train *against*. This is the
single blocker for the whole project.

### How to fix it
Capture the following per `Patient_ID` from the anaesthesia / theatre record, then derive `Decision`:

| Column | Values |
|---|---|
| `CL_grade` | 1–4 (Cormack–Lehane) |
| `Attempts` | 1, 2, 3, 4+ |
| `Adjunct` | Y/N (bougie, stylet, BURP, cricoid) |
| `Rescue_device` | Y/N (video laryngoscope, fiberoptic, LMA, surgical) |

```
Difficult  if Attempts >= 3  or CL_grade == 4  or Rescue_device == Y
Moderate   if Adjunct == Y   or CL_grade == 3  or Attempts == 2
Easy       otherwise
```

**If these records cannot be obtained at all**, the project must be re-framed before more model
work: either a rule-based checklist (no ML claims), a prospective collection plan, or an existing
public airway dataset with outcomes.

# 🟠 6. "Multimodal" is a label, not a capability

### What's wrong
The project is titled *Multimodal Difficult-Airway Prediction* and the plan lists five image
modalities. In reality:

- `backend/deploy/schemas.py:95` — `PredictionInput` has **30 tabular fields and zero image fields**
- the API loads `checkpoints/tabular_best.pt` and nothing else
- `backend/training/trainer.py:61` and `:95` hardcode `categorical_indices = []`, so the fusion path
  is dead code
- there is no `train_multimodal.py`
- `data/raw/Image Dataset/` holds 343 photos with **no manifest** linking them to patients or labels

### Why it matters
Anyone who reads the documentation and then the code finds two different projects. 5 of the 6
planned modalities are decorative. This is the kind of mismatch that fails a review.

### How to fix it
1. Immediately: add an honesty banner to `README.md` / `AGENTS.md` —
   *"tabular-only; images are collected but not labelled or used."*
2. Or build the image path properly: a label manifest, a written `train_multimodal.py`, and the
   fusion fix. That is a separate phase, not a side quest.

# 🟠 7. About half the input fields are empty

### What's wrong
Measured on the 125 real rows:

- **14 of 29 features are constant** — identical for every patient, so zero signal:
  `Disease_Arthritis`, `Disease_Down_Syndrome`, `Breathing_Snoring`, `Breathing_Sleep_Apnea`,
  `Symptom_Voice_Changes`, `Symptom_Difficulty_Swallowing`, `Injury_Swelling`,
  `Injury_Previous_Neck_Fracture`, `Previous_Emergencies_ICU`, `Neck_Structure`, `TMD_Category`,
  `Neck_Movement_Degrees`, `Neck_Movement_Category`, `Tissue_Flexibility`
- `Neck_Movement_Degrees = 85` for **all 125 patients** — a default fill, not a measurement
- **29 rows are exact duplicates** on features
- only ~15 columns vary at all, and several are coarse (`Mouth_Opening_mm` has 4 distinct values)

### Why it matters
A model can only learn from columns that change. Half the form is currently collecting nothing,
and an "always 85" field teaches the model that the feature is useless — which will stay true even
after you start collecting it properly, until you retrain.

### How to fix it
1. Fix the collection form before recruiting more patients.
2. Mark "not measured" explicitly instead of filling a default (85, 0, "Normal").
3. Re-audit variance after every 50 new patients; drop columns that stay constant.

# 🟠 8. Softmax temperature 5.0 hides miscalibration

### What's wrong
`backend/deploy/config.py:51` sets `model_softmax_temperature: float = 5.0`. Every prediction is
computed as `softmax(logits / 5.0)`.

### Why it matters
Dividing logits by 5 flattens the output so the API stops returning 99 % confidence. It treats the
symptom, not the cause. **Any probability the dashboard shows a clinician today is cosmetic** — it
has not been calibrated against anything real.

### How to fix it
1. Retrain on real labels.
2. Plot a reliability curve on held-out data.
3. Fit the temperature on a validation split — it should land near **1.0** if the model is healthy.
4. If it doesn't, fix the model, not the temperature.

# 🟠 9. Tests never check the model's behaviour

### What's wrong
The suite has 51 tests covering auth, sessions, rate limits, schemas and the API surface. Static
analysis of `MODEL_LOADER` reports **"no covering tests found"**. Nothing asserts that a patient
with a difficult airway is flagged as difficult.

### Why it matters
CI can be fully green while the model predicts garbage. A green check gives false confidence to
whoever reviews the project.

### How to fix it
1. Freeze a small labelled hold-out file.
2. Add one test: fail the build if Difficult-class recall drops below an agreed threshold.
3. Keep the temperature and model-version assertions next to it.

# 🟠 10. 125 patients is too few for a 3-class model

### What's wrong
At real prevalence (~5–15 % difficult), 125 patients contain roughly **6–19 difficult cases**.

### Why it matters
With 5-fold cross-validation each fold holds ~25 patients, so a single difficult case moves recall
by ~4 percentage points and confidence intervals land around ±20 points. A 3-class model cannot be
validated at this size — any number it produces is noise.

### How to fix it
1. Make the primary task **binary** (Easy vs Not-Easy) or an **ordinal severity score**.
2. Report per-class recall with **95 % bootstrap CIs**, never bare accuracy.
3. Use repeated stratified CV (5-fold × 10 repeats) instead of a single split.
4. Treat 3-class output as secondary and clearly labelled as exploratory.

# 🔴 11. No external or prospective validation

### What's wrong
Every metric in the repo comes from the same synthetic file the model was trained on. There is no
second hospital, no later time period, and no prospective collection.

### Why it matters
Even with perfect labels, a model validated only on its own data tells you nothing about the next
patient. This is the difference between a coursework demo and a clinical tool.

### How to fix it
1. State explicitly in every report: *"not externally validated; research prototype only."*
2. Plan a temporal split (train on earlier patients, test on later ones) as the minimum credible
   validation.
3. Never present the system as a clinical decision aid.

# 🔴 12. The LLM gives advice from an unvalidated model

### What's wrong
`backend/deploy/llm_assistant.py` builds a clinical summary and recommendations from the model's
prediction and the patient profile. The prediction behind it is generated from rule-made labels
(#1) with a flattened probability (#8).

### Why it matters
Fluent, confident clinical text is the most dangerous output in the system, because it reads like
advice. A wrong prediction wrapped in good prose is worse than no output at all — and the fallback
path already exists, so this content can appear even when the LLM is unreachable.

### How to fix it
1. Until the model is validated, show the LLM text as **"example output, not medical advice"** in
   the UI, and keep the `source: fallback|llm` badge visible (already implemented).
2. Do not let the LLM add facts the model did not produce.
3. Add a permanent non-dismissible disclaimer on every report.

# 🟡 13. ONNX export is broken

### What's wrong
`backend/deploy/export.py` builds a dummy input of `torch.randn(1, 20)` with an empty categorical
list. The real `TabularModel` expects 7 numerical + 22 categorical inputs.

### Why it matters
The exported artifact would not match the served model. Nothing currently depends on it, so it is
latent rather than active — but it will fail the moment someone tries to ship the ONNX file.

### How to fix it
Rewrite the dummy inputs to match `train_tabular.py` (`NUMERICAL_COLS`, `CATEGORICAL_COLS`,
`cat_cardinalities`), then assert the exported model's output matches PyTorch within tolerance.

## What is **not** a problem (checked)

- **Train/test leakage from the bootstrap augmentation.** The 2,500 rows come from 45 real seeds,
  which normally leaks. Tested: random split vs group-aware split gave 0.804 vs 0.809 — no
  meaningful inflation. The inflated numbers come from limitations #1 and #2, not the split.
- **Authentication and session handling.** Server-enforced sessions, `sid` claims, idle/absolute
  timeouts and rate limits are implemented and tested.
- **Secret handling.** JWT secret has a random per-boot backstop; no secrets are committed.
- **PHI containment.** `data/raw/` is gitignored and dockerignored.
